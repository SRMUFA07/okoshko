# План проекта «Окошко»

Живой план работ. Статусы: `[ ]` — не сделано, `[x]` — сделано. Выполненными отмечаются только реализованные и проверенные пункты. Приоритет сейчас — один законченный пользовательский поток, а не ширина функциональности.

## Продукт и границы первой версии

- [ ] Описать роли и основной сценарий клиента и мастера.
- [ ] Определить, что именно означает «подходящее время»: диапазоны, дни, горизонт ожидания и часовой пояс.
- [ ] Решить, подтверждает ли запись мастер или она автоматически закрепляется за первым успешно подтвердившим клиентом.
- [ ] Определить правила удержания/истечения предложения и поведение при одновременных подтверждениях.
- [ ] Определить минимальный состав первой версии и критерии её готовности.

## UI / Telegram WebApp

- [ ] Выбрать и создать frontend-стек Telegram WebApp.
- [ ] Сделать клиентский интерфейс подписки на мастера и предпочтения по времени.
- [ ] Сделать экран списка подписок и состояния предложений.
- [ ] Сделать интерфейс мастера для публикации и снятия свободного окна.
- [ ] Добавить состояния загрузки, пустого результата, ошибки и повторного действия.
- [ ] Проверить интерфейс в Telegram WebApp на мобильных размерах экрана.
- [ ] Диаграммы и расширенную аналитику рассмотреть после проверки основного потока.

## Backend / API

- [ ] Описать границы модулей и HTTP API для мастеров, предпочтений, слотов и подтверждений.
- [ ] Реализовать создание и отмену подписки клиента на мастера.
- [ ] Реализовать публикацию, изменение и снятие свободного слота мастером.
- [ ] Реализовать подбор клиентов по предпочтениям и отправку предложения.
- [ ] Реализовать конкурентно-безопасное подтверждение: слот получает не более одного клиента.
- [ ] Определить идемпотентность повторного запроса подтверждения и поведение при истечении предложения.
- [ ] Добавить проверку авторизации и прав на операции мастера и клиента.

## Данные и БД

- [ ] Определить сущности и построить ER-модель для мастеров, клиентов, подписок, предпочтений, слотов и бронирований.
- [ ] Построить даталогическую модель и определить ограничения целостности и уникальности.
- [ ] Обосновать нормализацию и места, где денормализация действительно нужна.
- [ ] Разобрать преобразование связей 1:1, 1:N и M:N в реляционную схему; зафиксировать выбранный вариант для каждой связи.
- [ ] Выбрать СУБД и механизм миграций на основании требований основного сценария.
- [ ] Реализовать схему и миграции для первого сквозного сценария.
- [ ] Продумать транзакционную стратегию и индекс для атомарного захвата слота.

## Telegram и уведомления

- [ ] Выбрать способ проверки Telegram WebApp `initData` на сервере и определить срок/контекст доверия к данным.
- [ ] Настроить отдельные dev/test бота и конфигурацию токенов через окружение.
- [ ] Реализовать привязку Telegram-пользователя к учётной записи приложения.
- [ ] Определить и реализовать шаблон уведомления о свободном окне и ссылку на подтверждение.
- [ ] Обработать ошибки Telegram API, ограничения частоты и повторную отправку уведомлений.

## Безопасность и приватность

- [ ] Составить модель угроз для подделки Telegram-пользователя, повторного использования init data и перебора подтверждений.
- [ ] Определить минимизацию и сроки хранения персональных данных.
- [ ] Защитить мастерские операции авторизацией и проверкой принадлежности ресурса.
- [ ] Добавить серверную валидацию, безопасную обработку ошибок и ограничение частоты чувствительных операций.
- [ ] Проверить отсутствие секретов и чувствительных данных в логах и репозитории.

## Тестирование и качество

- [ ] Добавить unit-тесты правил подбора и переходов состояний слота.
- [ ] Добавить интеграционный тест конкурентного подтверждения одного слота.
- [ ] Добавить тесты авторизации и проверки Telegram `initData`.
- [ ] Определить минимальный набор проверок для локальной разработки и CI.

## Инфраструктура и эксплуатация

- [ ] Определить среду размещения и купить/создать сервер после выбора требований и бюджета.
- [ ] Подготовить Docker-образ и локальный запуск зависимостей, когда появится реальная конфигурация приложения.
- [ ] Настроить конфигурацию окружений и управление секретами.
- [ ] Добавить health checks, базовые метрики и структурированные журналы без чувствительных данных.
- [ ] Описать резервное копирование и восстановление БД.
- [ ] Подготовить CI для сборки и проверок.

## Архитектура и масштабирование

- [ ] Проверить, достаточно ли модульного монолита для первой версии; отдельно фиксировать только подтверждённые причины усложнения.
- [ ] После появления измерений определить, нужен ли отдельный обработчик уведомлений или очередь задач.
- [ ] К мультиагентной разработке переходить после появления устойчивых границ модулей, интерфейсов и критериев проверки; сначала определить, какие параллельные задачи действительно независимы.

## Открытые решения

- Frontend-стек и способ локального запуска WebApp.
- СУБД и схема идентификации пользователей/мастеров.
- Кто является источником истины для «первым подтвердил»: атомарная фиксация на backend с каким пользовательским подтверждением.
- Нужно ли мастеру подтверждать клиента дополнительно, и как действовать при гонке.
- Где размещать первую рабочую версию и какие данные/регионы хранения необходимы.
