# Слоистая архитектура

Для backend зафиксирована простая слоистая структура Spring-приложения. API каталога и заявок подключены к PostgreSQL. Защищённые маршруты проверяют Telegram `initData` и роли; Telegram-бот и отправка уведомлений пока не реализованы.

## Слои

```text
controller -> service -> repository
                  ↕         ↕
                 dto      entity
```

- `controller` — HTTP-эндпоинты, разбор запросов, вызов сервисов и формирование ответов. Не содержит бизнес-логики и не обращается к БД напрямую.
- `service` — прикладные операции и бизнес-правила; координирует репозитории.
- `repository` — чтение и запись данных.
- `dto` — форматы входных и выходных данных API; не используются как сущности БД.
- `entity` — классы, соответствующие сохраняемым записям.

Основной поток вызова: `controller -> service -> repository`. DTO используются на границе API, entity — при работе с хранилищем. Контроллеры не должны зависеть от repository напрямую. Пакеты остаются простыми; дополнительные слои и пакеты, например `config`, добавляются только при конкретной необходимости.

## Пакеты Java

```text
com.okoshko
├── controller
├── service
├── repository
├── dto
└── entity
```

Пакеты созданы как каркас. Конкретные классы будут добавлены вместе с согласованным сквозным сценарием; сейчас намеренно нет фиктивных endpoint-ов, сущностей или бизнес-правил.

## Границы текущего решения

Все слои находятся в одном Spring Boot приложении. HTTP-слой подключён через Spring MVC, к PostgreSQL приложение обращается через JDBC и SQL-запросы из repository. URL задаётся через `DB_URL` (по умолчанию `localhost:5432/okoshko_db`), имя пользователя и пароль — через `DB_USERNAME` и `DB_PASSWORD`. Учетные данные в репозитории не хранятся. Пользователь решил пока вести изменения схемы повторно выполняемыми SQL-патчами, без отдельного migration framework.

## Изменения локальной схемы PostgreSQL

В локальную `okoshko_db` применены SQL-изменения, сохранённые в репозитории как повторно выполняемые патчи:

1. `teachers.user_id` уникален — у пользователя не более одного профиля учителя.
2. Роль `student` несовместима с `admin` и `teacher`; `admin` и `teacher` могут сочетаться. Проверка выполняется триггером при назначении или изменении ролей.
3. Заявка создаётся со статусом `pending` и может перейти в `approved` либо `rejected`; конечный статус не переводится обратно.
4. `requests.desired_time` хранит момент времени. Старые значения преобразованы как локальное время Уфы (`Asia/Yekaterinburg`).
5. Повторная отправка заявки использует UUID `idempotency_key`, уникальный для ученика.

Скрипты: [001_unique_teacher_user.sql](../db/patches/001_unique_teacher_user.sql), [002_exclusive_student_role.sql](../db/patches/002_exclusive_student_role.sql), [003_request_status_transitions.sql](../db/patches/003_request_status_transitions.sql), [004_request_time_zone.sql](../db/patches/004_request_time_zone.sql) и [005_request_idempotency.sql](../db/patches/005_request_idempotency.sql). Патчи применены непосредственно к локальной БД; отдельный migration framework не вводится. Схема поддерживает несколько групп-кандидатов на заявку.

Текущая DDL-схема без пользовательских записей и минимальный seed ролей зафиксированы в [`db/`](../db/README.md).
